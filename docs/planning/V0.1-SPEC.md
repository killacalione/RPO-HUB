# Version 0.1 scope specification

Planning checkpoint after seven interview rounds, 2026-10-14. This is a concrete feature specification, not implemented code or a release approval. Owner requirements and proposed technical choices are distinguished.

## Confirmed product scope

| Feature | Owner requirement | First-build acceptance proposal |
|---|---|---|
| Creation | Code/scripting and personalization | Two original worlds authored through a documented versioned SDK |
| Demo experience | Explore, personalize spaces, travel through portals | Personal choices survive travel and reload; recoverable local save/export in S1 |
| Personal-space access | Owner chooses visibility at creation | Proposed Private/Invite-only/Public modes with separate editing and server-checked online visits |
| Local coding | VS Code/GitHub workflow from start | Local project builds/previews and produces the same bundle as browser path |
| Browser coding | Integrated editor from start | Edit source, diagnostics/logs, Run/Stop, export/import and compatible bundle |
| Public worlds | Public sharing/social interaction | Public directory, versioned world pages, eligible joins and shared presence |
| Publishing | Trusted creators publish directly | Current trusted role releases automatically validated bundle without routine per-release human queue |
| Text | Text chat | World/party scope, message validation/rate limits and block/report controls |
| Proximity voice | Spatial voice in worlds | Distance/direction playback plus tested eligible-recipient authorization |
| Party voice | Group voice | Authorized membership, persistent party through world changes, visible outgoing route |
| Audience | Children, teens and adults; children communicate within age group | Defined cohorts/assurance and reviewed parent/contact/content permissions; hostile-client isolation evidence |
| Geography | Worldwide availability from first public release | Document lawful country-specific account/feature eligibility; global readiness remains incomplete |
| Owner effort | limited maintainer capacity | Bounded development plan; separately staffed live response/operations |
| Cost | Prefer free/lowest cost and education benefits | No required paid baseline for internal test; measured voice/backend usage and hard stops |

Visitors do not need to code. Avatar/profile personalization and world traversal support the initial vision; first controls, avatar format and visual art direction remain proposals. AI characters, pets, paid currency/creator payouts, native XR/AR and companion-device polish remain later milestones, with shared interfaces planned early. No selected feature is silently removed because it is expensive.

## Selected first-demo direction

Visitors explore, personalize a space and travel through portals. The proposed S1 loop is: explore a starter scene; choose colors/place and arrange approved props; save/export; travel to a second scene; return with choices intact. Creators still use code through both workflows. Separate versioned world templates from visitor configuration. Owner chooses personal-space visibility at creation; exact mode semantics/defaults and scene themes remain proposals; local saves do not claim online ownership or cross-device synchronization. See [demo design](DEMO-EXPERIENCE.md).

## Proposed technical foundation

One SDK/project contract across both coding paths, containing manifest, source, compiled script, asset references/content hashes, SDK/runtime version and declared capabilities. Candidate JS/TS and Babylon rendering; isolated QuickJS-in-Wasm worker runtime needs pinned adversarial tests. Candidate desktop browser Monaco with a lightweight mobile fallback; official Monaco does not support mobile browsers, and VS Code extensions do not automatically run in it [S66]. Both creators use the same validation and publish API. Avoid arbitrary npm installs/build hooks in the initial browser environment.

Trusted host/server owns identity, current publisher grants, world publication state, room membership, message permissions, durable state and media authorization. Trust grants don't turn scripts into platform code. Guest scripts do not control microphones, party membership, balances or private account objects. LiveKit is a media candidate; separate conventional Node and Workers/Durable Objects server designs must be tested, not assumed interchangeable.

## Proposed delivery sequence

1. **S1: SDK and dual authoring.** One local project and the integrated browser editor create the same two world bundles. Test exploration/personalization/portal return with draft preservation, Run/Stop, imports/exports and guest/runtime boundaries. Target no new subscriptions for the internal spike.
2. **S2: Shared local/social test.** Two or more actual clients enter a world, transition portals, use text, and exercise publish-role/room permissions through an authoritative server.
3. **S3: Voice routing test.** World/proximity and party channels, one microphone controller with room-specific track clones/wrappers, route indicators, deafen/mute/PTT, reconnect and world transitions. Prove prohibited track delivery stays denied with modified clients; attenuation/subscription UI alone is insufficient.
4. **S4: Trusted release pipeline.** Current grants, schema/runtime/resource/asset checks, immutable versions, public directory, rollback/quarantine and trust revocation. No routine human queue per trusted release, but operational reports/content enforcement remain.
5. **S5: First public all-age release.** Complete chosen child-parent/contact/jurisdiction flows and assign operating response ownership; test public discovery, selected media and removal/report workflows at measured limits.

All S1–S5 work remains unexecuted. Public release is the owner-required endpoint; internal/invited tests are preparatory. Owner limited maintainer capacity is confirmed; dates/capacity depend on actual devices, country/age policy, staffed response and resources. See [S1 brief](S1-IMPLEMENTATION-BRIEF.md).

## Decisions still needed for launch

Age-group child public communication and worldwide intent are selected. Still needed: exact bands/minimum age, assurance/parent process, country eligibility and operator; trust grants/minor publishing; live coverage/languages/response; credits and physical test devices. Owner limited maintainer capacity is effort, not guaranteed service coverage. Language/runtime/framework/host pins follow the bounded technical comparison. These launch questions do not erase the confirmed requirements.

## Personal-space access checkpoint

Owner choice at creation is confirmed. Proposed modes distinguish private owner-only visits, account-bound invited visits and public discovery/entry for eligible visitors. Viewing does not grant editing. Owners cannot override cohort/guardian/region/content/block rules. S1 preserves a requested-visibility preference; online stages require server checks, active revocation and protected-data/media denial tests. Private initial selection is proposed with applicable child high-privacy rules considered [S85]. See [space access](SPACE-ACCESS.md).

## Developer workflow requirement

Owner selects Codex, Hermes, Copilot and other agents, primarily cloud models that can be switched, with compatible local tool-use/reasoning models. Proposed portable instructions, common role text, task/capability records and client adapters preserve the same product acceptance. This is developer tooling, not a new first-release AI feature. See [workflow](AGENT-WORKFLOW.md) and [handoff](AGENT-HANDOFF.md). Actual client/model plans and runtime behavior remain untested.
